# R06 — retain a firing alert after recovery (draft for review)

Status: specification only. Scenario outputs below are proposed expectations,
not executed results. All inputs are controlled synthetic fixtures.

## Behavioural requirement — eligible for a future generation prompt

Metric: `service_error_ratio`, a supplied gauge, unitless fraction in [0,1].
Complete input labels, excluding the implicit metric name: exactly `service`,
a nonempty string. One series per service, stable labels, no other input or
external labels. Use the supplied ratio directly, without rate calculations.

Evaluate at 0m, 1m, 2m, etc. Complete finite observations are available for every
service at every evaluation. Each scenario starts with no pending or firing
alerts. Continuity refers to scheduled evaluations.

For each service, require a ratio **strictly greater than 0.05** continuously
for **two elapsed minutes** before initially firing. A value at or below 0.05
before firing resets the wait; a pending alert never receives firing retention.

Once firing, retain the alert for **three elapsed minutes starting at the
first evaluation where the condition is false**. If that evaluation is t,
the alert remains firing at t, t+1m and t+2m, and clears at t+3m if the condition
has remained false. Retention is anchored to the first false evaluation, not
the preceding true sample, and does not restart at every false sample.

If the condition becomes true while the alert is still retained, continue
firing without a second waiting period and cancel the current recovery timer.
The next false evaluation starts a new three-minute retention period. A true
condition exactly at the expiry evaluation also continues firing; evaluate
the current condition before resolving. After an alert has actually cleared,
a later true condition must satisfy a fresh two-minute wait. Timers and alert
identities are independent for each service.

Required alert name: `ServiceErrorRatioHighRetained`. Emit exactly one alert
per firing or retained service. Exact identifying labels: that `alertname`
and the original `service` value. No additional output labels or annotations
are permitted. Retention concerns the Prometheus firing state, not notification
repeat intervals, delivery delays or Alertmanager grouping.

## Review-only scenarios — exclude from generation prompts

Each list is at 0m, 1m, etc. `api` denotes exactly the required service=api
alert; `none` is an empty firing set. Listed ranges include every minute.

| Scenario | Input ratios | Expected firing set |
|---|---|---|
| Healthy | api: .01 .01 .01 .01 .01 | 0–4m: none |
| Strict equality | api: .05 .05 .05 .05 .05 | 0–4m: none |
| Spike never fires or gains retention | api: .01 .10 .01 .01 .01 .01 | 0–5m: none |
| Sustained with no recovery | api: .01 .10 .10 .10 .10 .10 | 0–2m: none; 3–5m: api |
| Full retention and exact expiry | api: .01 .10 .10 .10 .05 .01 .01 .01 .01 | 0–2m: none; 3–6m: api; 7–8m: none |
| Renewed breach during retention | api: .01 .10 .10 .10 .01 .10 .01 .01 .01 .01 | 0–2m: none; 3–8m: api; 9m: none |
| Breach exactly at expiry boundary | api: .01 .10 .10 .10 .01 .01 .01 .10 .01 .01 .01 .01 | 0–2m: none; 3–10m: api; 11m: none |
| New wait after actual clearance | api: .01 .10 .10 .10 .01 .01 .01 .01 .10 .10 .10 | 0–2m: none; 3–6m: api; 7–9m: none; 10m: api |
| Independent service timers | api: .01 .10 .10 .10 .01 .01 .01 .01 .01; web: .01 .01 .10 .10 .10 .01 .01 .01 .01 | 0–2m: none; 3m: api; 4–6m: api and web; 7m: web; 8m: none |

For full retention, firing starts at 3m. The first false observation at 4m
starts retention, which ends at 7m. In the renewed-breach case, high at 5m
cancels that timer; the low at 6m starts a new timer expiring at 9m.

Beyond R01: delayed clearance, expiry boundaries, cancellation of recovery
on a renewed breach, and re-arming after actual clearance. Review choice:
three-minute retention anchored to the first false evaluation. See
[semantics notes](SEMANTICS.md) for the pinned-version source check. These
expectations still need executable validation in a later authorized stage.
