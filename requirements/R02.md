# R02 — sustained latency (draft for review)

Status: specification only. Scenario outputs below are proposed expectations,
not executed results. All inputs are controlled synthetic fixtures.

## Behavioural requirement — eligible for a future generation prompt

Metric: `service_latency_p95_seconds`, a gauge holding an already computed
95th-percentile request latency for the preceding one-minute observation window.
Its unit is **seconds**; 0.5 seconds is 500 milliseconds. Values are finite and
nonnegative. Use the supplied value directly; do not calculate a percentile,
rate, increase, or a new time-window statistic.

Complete input label schema, excluding the implicit metric name: exactly
`service`, a nonempty string. There is exactly one series per service, with
stable labels and a complete sample at each one-minute evaluation. No `job`,
`instance`, `quantile`, environment, or other labels are present. No external
labels are configured. Each scenario starts with no pending or firing alerts.

Evaluate at 0m, 1m, 2m, and so on. For each service, trigger when the supplied
latency is **strictly greater than 0.5 seconds** continuously at evaluations
for **three elapsed minutes**. Equality does not qualify. A false evaluation
before firing resets the wait. Clear a firing alert at the first evaluation
at or below 0.5 seconds; no retention applies. Continuity refers to scheduled
observations, not unobserved between-sample behaviour.

Required alert name: `ServiceLatencyHigh`. Emit exactly one alert per affected
service. Its exact identifying labels are `alertname="ServiceLatencyHigh"`
and the original `service` value. No additional output labels or annotations
are permitted. Do not merge services.

## Review-only scenarios — exclude from generation prompts

Each list starts at 0m with one value per minute. `api` means exactly the
required alert for service=api; `none` means the entire firing set is empty.
Ranges below include every integer-minute evaluation in the range.

| Scenario | Inputs (seconds) | Expected firing set |
|---|---|---|
| Healthy | api: .10 .20 .30 .40 .20 .10 | 0–5m: none |
| Strict equality / units | api: .50 .50 .50 .50 .50 .50 | 0–5m: none |
| Too brief | api: .10 .80 .80 .10 .10 .10 | 0–5m: none |
| Boundary then recovery | api: .10 .80 .80 .80 .80 .50 | 0–3m: none; 4m: api; 5m: none |
| Interrupted wait | api: .10 .80 .10 .80 .80 .80 .80 | 0–5m: none; 6m: api |
| Service isolation | api: .10 .80 .80 .80 .80 .80; web: .20 .20 .20 .20 .20 .20 | 0–3m: none; 4–5m: api only |

For the boundary case, high observations at 1m, 2m and 3m span only two
minutes; firing begins at 4m. The value .80 must be understood as 800 ms,
not 0.80 ms or 800 seconds.

Beyond R01: correct use of a supplied latency gauge in seconds and a different
persistence duration (3m). This deliberately reuses the same basic temporal
mechanism as R01; it is not an independent new alert-state mechanism.

Review choices: proposed 500 ms threshold, three-minute wait, precomputed p95,
and exact-label/no-annotation policy. See [semantics notes](SEMANTICS.md).
