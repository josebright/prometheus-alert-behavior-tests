# R03 — any instance, one alert per service (draft for review)

Status: specification only. Scenario outputs below are proposed expectations,
not executed results. All inputs are controlled synthetic fixtures.

## Behavioural requirement — eligible for a future generation prompt

Metric: `service_instance_error_ratio`, a supplied gauge, unitless fraction
in [0,1]. Complete input labels, excluding the implicit metric name: exactly
`service` and `instance`, both nonempty strings. One series exists per unique
(service, instance) pair. Instance names need only be unique within a service.
The instance set and all labels remain fixed within a scenario. No other input
or external labels exist. Use the ratio directly, without rate calculations.

Each declared instance has a complete, finite sample at 0m, 1m, 2m, etc.,
available before the corresponding evaluation. Evaluate every minute, starting
with no pending or firing alerts. Every represented service has at least one
instance. Continuity is defined at these evaluations.

For each service, the condition holds if **at least one** of its instances
has a ratio **strictly greater than 0.05**. Require that service-level condition
to hold for **two elapsed minutes** before firing. The breaching instance may
change during the waiting period: continuity belongs to the service, not to a
particular instance. Do not use an average or sum of instance ratios as the
criterion. If all of a service's instances are at or below 0.05, reset a pending
wait or immediately clear its firing alert. No additional retention applies.

Required alert name: `ServiceAnyInstanceErrorHigh`. Emit exactly one alert per
affected service, even if multiple instances breach. Exact identifying labels:
`alertname="ServiceAnyInstanceErrorHigh"` and the original `service` value.
Remove `instance` from the alert identity. No additional output labels or
annotations are permitted. Services must remain independent.

## Review-only scenarios — exclude from generation prompts

Each series has one value at 0m, 1m, etc. `api/a` denotes service=api,
instance=a. All listed series are present throughout their row. `api` in the
output means exactly one required service=api alert, without instance.

| Scenario | Input ratios | Expected firing set |
|---|---|---|
| All healthy | api/a: .01 .01 .01 .01 .01; api/b: .02 .02 .02 .02 .02 | 0–4m: none |
| Strict equality | api/a: .05 .05 .05 .05 .05; api/b: .01 .01 .01 .01 .01 | 0–4m: none |
| One breach; average would hide it | api/a: .01 .09 .09 .09 .09; api/b: .01 .01 .01 .01 .01 | 0–2m: none; 3–4m: api |
| Multiple breaching instances | api/a: .01 .10 .10 .10 .10; api/b: .01 .20 .20 .20 .20 | 0–2m: none; 3–4m: api exactly once |
| Instance handoff without interruption | api/a: .01 .10 .01 .01 .01; api/b: .01 .01 .10 .10 .10 | 0–2m: none; 3–4m: api |
| Service-wide interruption | api/a: .01 .10 .01 .10 .10 .10; api/b: .01 .01 .01 .01 .01 .01 | 0–4m: none; 5m: api |
| Recovery of all instances | api/a: .01 .10 .10 .10 .05 .01; api/b: .01 .01 .01 .01 .01 .01 | 0–2m: none; 3m: api; 4–5m: none |
| Separate services, reused instance name | api/a: .01 .10 .10 .10 .10; web/a: .01 .01 .01 .01 .01 | 0–2m: none; 3–4m: api only |

In the handoff case the service condition first holds at 1m and never becomes
false, although the violating instance changes at 2m. Firing must begin at 3m.

Beyond R01: existential aggregation across instances while retaining service
identity, including deduplication and service-level continuity across handoffs.
Review choice: service-level persistence is proposed, rather than requiring
one particular instance to breach for the entire period. See
[semantics notes](SEMANTICS.md).
