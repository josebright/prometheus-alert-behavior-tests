# R01 — behavioural contract, written before the reference rule

Use the supplied synthetic `service_error_ratio` gauge directly, once per
minute, independently for each service. The ratio must be strictly above
0.05 at every evaluation for two elapsed minutes before firing. Preserve
`service`. Clear at the first evaluation at or below 0.05. Assume complete
observations, one series per service, and no additional alert retention.
Do not apply rate(). Continuity here means continuity observed at scheduled
evaluations; no claim is made about unobserved changes between samples.

All sequences below are synthetic fixtures. Each number is a sample at
0m, 1m, 2m, etc.; each listed timestamp is explicitly asserted. `none` means
an empty firing set. `api` means exactly one alert with identifying labels
`alertname=ServiceErrorRatioHigh, service=api`; no annotations or extra labels.
The two-service case must never include `service=web`.

| Fixture | Input values | Expected firing assertions |
|---|---|---|
| healthy | api: .01 .02 .03 .04 .01 | 0,1,2,3,4m: none |
| brief spike | api: .01 .10 .01 .01 .01 | 0,1,2,3,4m: none; spike at 1m resets at 2m |
| sustained | api: .01 .10 .10 .10 .10 | 0,1,2m: none; 3,4m: api |
| recovery | api: .01 .10 .10 .10 .05 .01 | 0,1,2m: none; 3m: api; 4,5m: none |
| two services | api: .01 .10 .10 .10 .10; web: .01 .01 .01 .01 .01 | 0,1,2m: none; 3,4m: api only |
| strict equality | api: .05 .05 .05 .05 .05 | 0,1,2,3,4m: none |
| interrupted persistence | api: .01 .10 .01 .10 .10 .10 | 0,1,2,3,4m: none; 5m: api |

For sustained errors, first active evaluation is 1m, only one minute has
elapsed at 2m, and two minutes have elapsed at 3m. Three high observations
at 1m, 2m, 3m span two minutes. Recovery at 4m must clear immediately,
including when the value is exactly the threshold.

For interrupted persistence, the high observation at 1m starts a waiting
period, but the low observation at 2m interrupts it. The next two-minute
waiting period starts at 3m. Only one minute has elapsed at 4m; two minutes
have elapsed at 5m. Therefore there is no firing alert at 0m through 4m,
and exactly `alertname=ServiceErrorRatioHigh, service=api` at 5m. Time spent
above the threshold before the interruption does not count toward this period.

The test's `exp_labels` omits alertname because promtool selects it using
`alertname`; the actual alert identity still includes that label. Empty firing
assertions do not directly inspect every internal pending state.
